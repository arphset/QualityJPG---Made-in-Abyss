# 📸 QualityJPG

**Поиск технического брака на фото для объявлений и маркетплейсов**

Загрузите фото — система измерит резкость, экспозицию, композицию и качество файла,
сведёт измерения в оценку из 10, объяснит каждый снятый балл и подскажет, как переснять.

## Что это за система

QualityJPG — информационная система, которая проверяет фотографию **до публикации** в объявлении
или карточке товара. Она не «смотрит» на фото как человек, а **синтезирует техническое описание
снимка** из нескольких независимых измерений:

- насколько резкие края и нет ли смаза;
- правильно ли выставлен свет: не темно ли, не выбиты ли света, нет ли засветки и контрового света;
- где на кадре главный объект и сколько места он занимает;
- достаточно ли разрешение, не пережат ли JPEG, нет ли цифрового шума.

Из этих измерений складывается **оценка из 10**, **список дефектов** с ценой каждого в баллах
и **рекомендации**, которые пишет локальная языковая модель (Ollama). Все вычисления идут на вашем
сервере — фото не отправляются во внешние облачные API.

## Технический брак, а не эстетика

QualityJPG отвечает на один практический вопрос: **разглядит ли покупатель товар на этом фото?**

| Система оценивает (технический брак) | Система **не** оценивает (эстетика и смысл) |
|---|---|
| размытие, смаз, «мыло» | красиво ли фото, удачен ли ракурс |
| темно, пересвет, засветка, низкий контраст | стиль, настроение, цветовая гамма |
| объект против окна или солнца | подходит ли фон и антураж к товару |
| товар слишком мелкий или у края кадра | правильный ли товар изображён, нет ли лишних предметов |
| маленькое разрешение, пережатый JPEG, шум | художественный замысел (намеренное размытие, туман, low-key) |

Поэтому **10/10 означает «технических дефектов не найдено»**, а не «лучшее фото на маркетплейсе».
Красивое, но мутное фото получит низкий балл; скучное, но резкое и хорошо освещённое — высокий.
Художественные снимки (длинная выдержка, намеренный засвет, силуэт против окна) система оценит
как брак — так и задумано: для карточки товара это действительно проблема.

Каждая оценка **объяснима**: отчёт показывает не просто «6/10», а конкретные причины
(«Размытие −4.3», «Пересвет, выбитые света (35%) −2.0», «Артефакты сжатия JPEG −2.0»),
и продавец сам решает, что исправлять.

## Как устроен анализ

```
 файл JPG/PNG
     │  чтение (PNG с прозрачностью → на белом фоне, как на маркетплейсе)
     ▼
 рабочая копия 1024 px ──────────────┐            исходный файл
     │                               │                 │
     ▼                               ▼                 ▼
 1. ГЛАВНЫЙ ОБЪЕКТ             2. РЕЗКОСТЬ        5. КАЧЕСТВО ФАЙЛА
 однородный фон → YOLOv8 →     ширина краёв       разрешение, JPEG-качество
 GrabCut → «не выделен»        по объекту         из таблиц квантования
     │ маска объекта           + 4 направления
     ├──────────────────────►  + шум
     ▼
 3. ЭКСПОЗИЦИЯ                 4. КОМПОЗИЦИЯ
 темно / пересвет / засветка   доля кадра под объектом,
 / тени / контраст / контровой смещение от центра
     │
     ▼
 ОЦЕНКА ИЗ 10  (плавные штрафы, потолок у каждой группы)  →  список дефектов
     │
     ▼
 LLM (Ollama qwen2.5:3b): текст «Оценка качества» + «Рекомендации»
```

Порядок важен: сначала находится **главный объект**, и уже по нему считаются резкость и экспозиция.
Так белый фон не считается пересветом, размытый фон за резким товаром — размытием,
а чёрный товар — недосветом.

## Методы и почему именно они

### 0. Рабочая копия 1024 px
Все измерения (кроме качества файла) идут на копии с длинной стороной 1024 px (`INTER_AREA`).
Фото 4000 px с телефона и скриншот 1000 px оцениваются в одном масштабе — именно в таком их увидит
покупатель. Заодно анализ занимает меньше секунды.

### 1. Выделение главного объекта — `filters/subject.py`
Три способа по очереди, от самого надёжного:

| Способ | Как работает | Когда срабатывает |
|---|---|---|
| **Однородный фон** | Медианный цвет полосы по краям кадра в Lab; объект — пиксели с ΔE > 16 от фона; морфология, мелкие пятна отбрасываются | Студийная съёмка на белом/сером/цветном фоне — **любой** товар, без классов |
| **YOLOv8n** | Крупные (> 3% кадра) уверенные (≥ 0.3) объекты с центром не дальше 35% от центра кадра | Люди, машины, мебель, техника в обычной обстановке |
| **GrabCut** | Сегментация от центральной области кадра | YOLO не узнал объект (например, машину в необычном ракурсе) |

Почему не только YOLO: он знает 80 классов COCO и не находит косметику, посуду, инструменты,
а случайный прохожий у края кадра становился «товаром». Для GrabCut-объекта уверенность ниже:
резкость тогда меряется по всему кадру, а штраф за заполнение вдвое мягче.

### 2. Резкость — `filters/blure_filter.py`
**Ширина краёв.** Кадр делится на блоки 32×32; в каждом блоке с заметным перепадом яркости
(p98 − p2 ≥ 20) ширина края ≈ перепад / максимум градиента Собеля. У резкого фото перепад проходит
за ~2 пикселя, у размытого растягивается до 4–10.

- **Только блоки с деталями.** Однотонные области (небо, белый фон, глянцевый кузов, чёрная ткань)
  не участвуют. Классическая дисперсия лапласиана здесь ошибалась: «тонула» в однотонных областях
  и зависела от разрешения — резкие фото гладких товаров считались размытыми.
- **25-й перцентиль по блокам объекта** — фото резкое, если резка заметная часть объекта.
  Боке и размытый фон за резким товаром не штрафуются.
- **4 направления.** Смаз движения размывает только края, перпендикулярные движению. Ширина считается
  отдельно по направлениям (тензор структуры блока); худшее направление входит в оценку с весом 0.6.
- **Шум.** На шумных фото перед расчётом применяется медианный фильтр 3×3 — иначе шум «изображает»
  резкие края и маскирует размытие.

Итог — индекс чёткости 0..1: ≥ 0.85 — резко, 0.45–0.85 — пограничная чёткость, < 0.45 — размыто.

### 3. Экспозиция — `filters/brightness_filter.py`
Каждая проблема получает степень 0..1, а не «да/нет».

| Проблема | Метод | Почему так |
|---|---|---|
| Слишком темно | 99-й перцентиль канала V (max R,G,B) по кадру | Тёмный товар на светлом фоне — норма; недодержка — когда светлых участков нет нигде. V, а не яркость: насыщенный красный товар не «тёмный» |
| Пересвет | Доля выбитых пикселей (V ≥ 253) **внутри объекта** и «упор в потолок»: выбитых больше, чем просто светлых (200–252) | У нормального фото света плавно сходят на нет, у передержанного — копятся у 255. Белый фон маркетплейса не считается. Небо/окно в сценах — с половинным весом |
| Засветка | Нет теней ни в кадре (p2), ни на объекте (p5) | Мутный «молочный» кадр |
| Провалы в тенях | Доля пикселей ≤ 5 на объекте, порог высокий | Чёрный товар сам по себе почти чёрный |
| Низкий контраст | p98 − p2 по кадру | Туман, пелена, грязный объектив |
| Контровой свет | Объект тёмный, фон намного светлее и местами выбит; только для неоднородного фона | Съёмка против окна/солнца. Детектор осторожный — ловит явные силуэты |

Выбитые блики, полностью окружённые товаром, считаются частью товара; крупные «дыры»
(фон внутри кольца или ручки кружки) — нет.

### 4. Композиция
Доля кадра, занятая рамкой объекта: ≥ 25% — без штрафа, меньше — штраф растёт до 5%.
Смещение от центра штрафуется, только если объект мелкий.

### 5. Качество файла — `filters/artifacts.py`, `main.py`
- **Разрешение.** Меньше 800 px по длинной стороне — штраф, растущий нелинейно: 600 px ≈ −1, 300 px — −4.
- **Сжатие JPEG.** Качество 1..100 восстанавливается из **таблицы квантования** в самом файле
  (обратная формула масштабирования стандартной таблицы IJG). Пиксельные метрики «квадратиков»
  проверялись и отброшены: по ним обычные веб-JPEG (качество 75–90) неотличимы от пережатых до 12.
  Ниже ~55 — штраф.
- **Цифровой шум.** Отклик ядра Иммеркера (почти нулевой на плавных градиентах) по блокам 8×8,
  берутся 2% **самых гладких** блоков: шум есть и там, а текстура травы, гравия или ткани — нет.

### 6. Оценка — `filters/score_calculator.py`
Оценка = 10 − штрафы, в диапазоне 1..10. Все штрафы **плавные** (без скачков на порогах),
у каждой группы — **потолок**; если сумма в группе выше потолка, все её штрафы ужимаются
пропорционально, и каждая проблема остаётся видна в отчёте.

| Группа | Потолок | Что входит |
|---|---|---|
| Чёткость | 5.5 | размытие, смаз, пограничная чёткость |
| Экспозиция | 4.0 | темно, пересвет, засветка, тени, контраст, контровой свет |
| Композиция | 2.5 | заполнение кадра, смещение, объект не выделен (−0.5) |
| Качество файла | 4.5 | разрешение, сжатие JPEG, шум |
| Пустой кадр | 4.0 | почти нет деталей — оценивать нечего |

Вердикты: 🏆 Отлично (≥ 9) · ✅ Хорошо (≥ 7.5) · ⚠️ Удовлетворительно (≥ 6) · ❌ Плохо (≥ 4) · 🚫 Критично.

### 7. Рекомендации LLM — `ollama/ollama_access.py`
Локальная модель **не ставит оценку** — она только объясняет её человеческим языком.
Ключевые выводы («фото размытое», «заполнение в норме») вычисляются в коде по тем же порогам,
что и балл, и передаются в промпт готовыми фразами, поэтому текст не спорит с оценкой.
Ответ выводится потоком; если модель не дописала раздел «Рекомендации», он достраивается
из списка найденных дефектов.

## Как проверялась оценка

Пороги подбирались на ~250 уникальных фото (товары на белом фоне, бытовые фото, пейзажи, улицы,
архивные снимки с Wikimedia, случайные фото picsum) и их **искусственно испорченных копиях**:
гауссово размытие, смаз движения, недодержка, передержка +1.5/+2.5 EV, пережатие JPEG,
шум, уменьшение до 300 px.

Итоговая проверка — на **свежем наборе**, который не участвовал в подборе порогов
(80 фото + 320 испорченных копий):

| | Результат |
|---|---|
| Хорошие фото: средний балл | 9.45 из 10, ниже 6 — 2 из 80 |
| Размытие, смаз, недодержка, низкое разрешение, сжатие JPEG, шум | найдено 40/40 по каждому виду |
| Передержка +1.5 EV / +2.5 EV | найдено 31/40 / 35/40 |
| **Весь брак** | **96%** найдено |

Для сравнения, первая версия ставила хорошим товарным фото в среднем 5.4, а их размытым копиям — 4.1:
разница в 1.2 балла. Сейчас — 9.5 против 4.2.

## Ограничения

- **Не эстетика.** Ракурс, фон, стиль и «продающесть» фото не оцениваются (см. выше).
- **Передержка** ловится не вся: часть сильно осветлённых снимков получает 7.5+.
  Мягкая молочная дымка без чисто белых пикселей почти не замечается.
- **Контровой свет** — только явные силуэты против яркого окна или неба.
- **Пересохранённый JPEG**: если пережатое фото сохранили заново с высоким качеством,
  «квадратики» не обнаруживаются (в файле записано новое качество).
- **Ложные срабатывания**: размытый передний план (решётка перед объектом), намеренная длинная
  выдержка, мягкие направленные текстуры (волны) могут считаться размытием или смазом;
  графика и сканы (карты, гравюры) — пересветом и шумом.
- **Шкала щедрая**: фото без дефектов почти всегда получает 9–10 — система не отличает
  «хорошее» от «отличного».
- Сессия хранится в памяти Streamlit: после обновления страницы (F5) нужно войти снова.
- Время ответа LLM зависит от CPU хоста: Ollama работает без GPU.

## Архитектура

```
Web-Client (браузер)
      │ HTTP / WebSocket
Web-server (Streamlit, frontend/)
      ├── I_ML_ANALYSIS  → ML&CV_Module/ (OpenCV, YOLOv8n, GrabCut, Ollama qwen2.5:3b)
      ├── I_DATA_ACCESS  → database/ (PostgreSQL 16, psycopg2)
      └── I_FILE_STORAGE → frontend/uploads/ (файлы под UUID, связь с БД по storage_filename)
```

Соответствует диаграмме компонентов из ТЗ; сценарии — диаграммы последовательностей
«Загрузка и анализ фото» и «Просмотр статистики».

**Технологии:** Python 3.11 · Streamlit 1.41 · OpenCV · NumPy · Pillow · Ultralytics YOLOv8n ·
Ollama (OpenAI-совместимый API) · PostgreSQL 16 · Altair · Docker Compose.

## Запуск

Нужны Docker Desktop и [Ollama](https://ollama.com) на хост-машине с моделью `qwen2.5:3b`:

```bash
ollama pull qwen2.5:3b
docker compose up -d --build
```

Приложение: <http://localhost:8501>. При первом запуске создаётся администратор из переменных
`ADMIN_LOGIN` / `ADMIN_PASSWORD` (по умолчанию `admin` / `admin12345` — **смените перед эксплуатацией**,
например через файл `.env` рядом с `docker-compose.yml`). Продавцы регистрируются сами.

Код смонтирован в контейнер; после изменения Python-кода перезапустите приложение:
`docker restart qualityjpg_app`.

### Переменные окружения (сервис `app`)

| Переменная | Назначение | По умолчанию |
|---|---|---|

| `APP_TIMEZONE` | Часовой пояс статистики | `Europe/Moscow` |

```bash
docker exec qualityjpg_app python tests/run_tests.py    # 52 теста, протокол → tests/results/
docker exec qualityjpg_app python tests/benchmark.py    # замер времени отклика (R.01.01)
```

Среди тестов — проверки поведения оценки (`test_ml.ScoringBehaviourTest`): белый фон не пересвет,
тёмный товар не недосвет, размытие, недодержка, низкое разрешение, сжатие JPEG и шум обнаруживаются,
PNG с прозрачностью читается на белом. Тесты используют отдельную БД `qualityjpg_test` и временную
папку хранилища — рабочие данные не затрагиваются. Протокол испытаний спринта 4:
[docs/TEST_REPORT.md](docs/TEST_REPORT.md).

## Развитие проекта

- Проверка на **реальных** плохих фото из объявлений (сейчас брак в основном искусственный)
  и замер совпадения вердикта с оценкой эксперта.
- Кнопка «оценка неверна» в отчёте — сбор обратной связи для подстройки порогов.
- Детектор мягкой засветки-дымки и более чувствительный детектор передержки.
- Визуальная LLM (например, qwen2.5-vl через Ollama) для смыслового анализа: узнать товар
  редкой категории, отличить художественный приём от брака.
- Отдельная модель эстетики (NIMA, LAION Aesthetic Predictor) — **дополнительная** оценка
  рядом с технической, а не вместо неё.
